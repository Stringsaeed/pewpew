## Recommended base

Use **candidate 1** as the base. It is the only design that closes the full proof loop: each level has a fixed compiled track, the phone and verifier call the same step function, replay consumes the recorded input stream, and the verifier compares a state hash. Its recursive readonly `WorldView`, caller-owned event buffer, exhaustive mappings, bounded SoA pool, renderer-owned particles, audio voice caps, and HUD identity bailout also cover the boundary and frame-budget criteria with concrete mechanisms. Candidate 2 is more complete as a campaign-data sample, but its determinism story stops short of cross-engine replay and its sketch publishes too many internal types. Candidate 3 has a compact batching idea, but its writable typed-array views violate a hard requirement and its hidden simulation ownership makes the central API difficult to implement safely.

## Grafts

- From **candidate 2**, graft the complete `CAMPAIGN.levels` 30-row tuple and the `defineCampaign` runtime validator, adapting the rows to candidate 1's fixed `seed`, `RAMP`, and `LevelSpec` contract rather than retaining caller-selected seeds.
- From **candidate 2**, graft the `BossPhaseSpec[]` shape so boss behavior remains row data when later bosses need health-gated phases.
- From **candidate 3**, graft the per-`Archetype` dense partitions in `Store` and `CAP` only if profiling shows candidate 1's per-frame mesh counting sort matters; preserve candidate 1's readonly projection instead of `ArchetypeView`'s raw mutable arrays.
- From **candidate 3**, graft the total `MeshSet = { [K in Archetype]: Mesh }` concept into the generator output so adding a gameplay archetype requires a generated mesh or an explicit non-mesh classification.

## Hard architectural requirement audit

- **Candidate 1:** No architectural requirement is contradicted; its sketch is incomplete rather than implementation-ready because `LEVELS` contains rows 1 and 10 plus TODOs, so requirement 1 cannot be executed until all 30 rows and the `NI()` bodies exist.
- **Candidate 2:** Requirement 1 is not fully satisfied because the design does not constrain cross-engine math or replay a recorded input stream to a state hash, so the Node verifier cannot prove Hermes reaches the same state.
- **Candidate 3:** Requirement 3 is violated because `ArchetypeView` exposes mutable typed-array elements to the renderer; requirement 1 is also under-specified because its replay compares only outcome and score and does not control cross-engine floating-point operations.
