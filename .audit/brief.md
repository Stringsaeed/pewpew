# pewpew: rocket arcade game. Shared brief for every agent on this run

Read this whole file before any work. It is the contract. Do not edit it.

## Product

A mobile arcade game. The player flies a rocket upward through space. 30 levels. Boss every 10 levels (levels 10, 20, 30).

- Core loop: the rocket auto-flies up through a level of fixed length. The player drags a finger horizontally (anywhere on screen) to steer left/right. Laser auto-fires. Hazards: asteroids (shootable, split into fragments), mines (explode on contact, cannot be shot), drones (fly patterns, shoot back), gravity wells (pull the rocket sideways). Pickups: crystals (score), shield (absorb one hit), rapid-fire (temporary). The level ends when the rocket reaches the wormhole at the end of the track. Three lives per level attempt. Score, best score per level, stars (1 to 3) per level persisted on device.
- Difficulty ramps across 30 levels via a data table: scroll speed, hazard density, hazard mix, drone patterns, gravity well count, track length, boss stats. The table is the single source of truth; nothing else hardcodes per-level rules.
- Screens: title, level select (30 tiles showing stars and lock state), gameplay with HUD (score, lives, level progress bar, shield state), pause, level complete (stars, score, next), game over (retry), settings (music/sfx toggles).
- Art: every mesh is generated by our own script (rocket from a lathe profile, asteroids as noisy icospheres, drones, mines, crystals, boss). Flat-shaded, vertex colors, neon palette on near-black. Particle exhaust and explosions. Scrolling starfield. No external assets, no image files beyond the app icon.
- Audio: every sound is synthesized at runtime by our own code using the Web Audio API clone react-native-audio-api. Music: a looping chiptune-style track per tier (levels 1-10, 11-20, 21-30, boss) built from a sequencer over oscillators with filters and envelopes. SFX: laser, hit, explode, pickup, shield, level complete, game over, UI tap. No audio files.

## Tech constraints (verified facts)

- Expo SDK 57 (expo ~57.0.27), react-native 0.86.3, react 19.2.3, TypeScript. Dev build via `npx expo prebuild` + `npx expo run:ios`. New Architecture is on by default and required.
- Rendering: `react-native-webgpu@0.5.17` (the package `react-native-wgpu` is a deprecated shim that re-exports it). Peer deps: `react-native-reanimated>=4.2.1`, `react-native-worklets>=0.7.2`. No Expo config plugin ships in 0.5.17; CocoaPods autolinking is enough. Simulator: Metal API validation may need to be off; verify at build time.
  - API: `import { Canvas, useCanvasRef, useDevice } from "react-native-webgpu"`. `<Canvas ref={ref} style={...} />`. `const ctx = ref.current.getContext("webgpu")` (sync, retry next frame if layout size is 0). `navigator.gpu.requestAdapter()` / `adapter.requestDevice()` or the `useDevice()` hook. `ctx.configure({ device, format: navigator.gpu.getPreferredCanvasFormat(), alphaMode: "opaque" })`. Render loop with `requestAnimationFrame`. After `device.queue.submit([...])` always call `ctx.present()` (RN only). Pixel density: set `ctx.canvas.width = clientWidth * PixelRatio.get()` and same for height. Globals `GPUBufferUsage`, `GPUTextureUsage`, `GPUShaderStage` exist on the main JS runtime.

Standard Web Audio semantics: `osc.frequency.setValueAtTime`, `gain.gain.exponentialRampToValueAtTime`, `node.start(t)`, `node.stop(t)`, `ctx.currentTime`.
- Persistence: `@react-native-async-storage/async-storage` or `expo-sqlite` kv store. Pick one.

## Hard architectural requirements

1. The game simulation is pure TypeScript with no React, React Native, WebGPU, or audio imports. Fixed timestep. Deterministic given (level table, seed, input stream). A Node script `scripts/verify-levels.ts` must be able to run a scripted bot through all 30 levels headless and assert each is completable and that the difficulty table is monotone where it should be. This is the proof of "30 levels" and runs in CI.
2. The data shape comes first. Name the game state model, the level table type, the entity representation, the event stream the sim emits (for audio and particles), and the input model before writing logic. Prefer a state machine for screen/phase flow over scattered booleans, a table for levels and entity archetypes, and a typed event list for sim-to-audio/sim-to-render communication.
3. Renderer reads sim state, never mutates it. Audio reacts to sim events, never polls sim internals.
4. Meshes are generated by `scripts/gen-meshes.ts` into a checked-in TypeScript module (positions, normals, colors, indices as typed arrays). Rerunning the script is the review mechanism.
5. Music and SFX are defined as data (note tables, envelopes, patch definitions) interpreted by one small synth engine. Rerunning is not needed; the data is the artifact.
6. Keep call chains short. A reader should trace input to pixels in at most three files.
